## 1. System Context

### 1.1 Призначення та межі (Scope)

Novelize є інформаційною системою контролю структурної та змістової цілісності художніх текстів. Система зберігає ієрархічну структуру твору, веде реєстр сутностей (персонажі, локації, події) у графовій моделі та асинхронно аналізує текст.

**У межах системи:** управління обліковим записом, ієрархія твору з версіюванням, реєстр сутностей, асинхронна перевірка мови, стилістичний аналіз, перевірка змістової узгодженості, доставка результатів у реальному часі, моніторинг.

**Поза межами системи:** мобільні клієнти, генерація тексту моделями LLM, офлайн-режим, платіжні операції, експорт у друковані формати.

### 1.2 Зовнішнє середовище

| ID | Зовнішній елемент | Тип | Інтерфейс |
|---|---|---|---|
| ACT-01 | Автор | Користувач | HTTPS, WSS |
| ACT-02 | Редактор (читання та коментування книги) | Користувач | HTTPS |
| EXT-01 | SMTP-провайдер | Зовнішній сервіс | SMTP / TLS |

### 1.3 Еталонне середовище вимірювань

Усі чисельні NFR вимірюються в еталонному середовищі: одна машина, 4 vCPU, 16 ГБ RAM, SSD, Docker Compose, один екземпляр кожного контейнера. Будь-яке збільшення цільових показників потребує окремого рішення (ADR).

## 3. Non-Functional Requirements

| ID | Категорія | Вимога | Поріг |
|---|---|---|---|
| <a id="srs-nfr-perf-01"></a>SRS-NFR-PERF-01 | Продуктивність | Синхронні ендпоінти повинні обслуговувати навантаження 500 RPS у еталонному середовищі. | Latency p95 < 200 мс; частка помилок < 0.1% |
| <a id="srs-nfr-perf-02"></a>SRS-NFR-PERF-02 | Обробка тексту | Асинхронний аналіз фрагмента до 50 000 символів повинен завершуватися від публікації події до події `analysis.completed`. | p95 ≤ 30 с при 10 одночасних аналізах |
| <a id="srs-nfr-perf-03"></a>SRS-NFR-PERF-03 | Реальний час | Результат аналізу повинен бути доставлений клієнту після появи події. | p95 ≤ 1 с |
| <a id="srs-nfr-perf-04"></a>SRS-NFR-PERF-04 | Граф | Перевірка узгодженості на графі до 10 000 вершин повинна виконуватися. | p95 < 2 с |
| <a id="srs-nfr-sec-01"></a>SRS-NFR-SEC-01 | Автентифікація | API Gateway і кожен сервіс повинні перевіряти підпис (RS256), `exp` та `aud` JWT; запит без чинного токена повинен отримувати HTTP 401. | 100% запитів із недійсним токеном відхилено |
| <a id="srs-nfr-sec-02"></a>SRS-NFR-SEC-02 | Rate Limiting | Система повинна обмежувати кількість запитів користувача та відповідати HTTP 429 з заголовком `Retry-After`. | 100 запитів / хв на користувача |
| <a id="srs-nfr-sec-03"></a>SRS-NFR-SEC-03 | OWASP Top 10 | Кодова база та образи повинні не містити вразливостей високого рівня. | 0 Critical/High у SAST, DAST та сканері образів |
| <a id="srs-nfr-sec-04"></a>SRS-NFR-SEC-04 | Транспорт | Зовнішній трафік повинен передаватися TLS 1.2 або вище. | 100% зовнішніх з'єднань |
| <a id="srs-nfr-sec-05"></a>SRS-NFR-SEC-05 | GDPR | Журнали подій не повинні містити адрес електронної пошти та паролів. | 0 збігів у журналах тестового прогону |
| <a id="srs-nfr-sec-06"></a>SRS-NFR-SEC-06 | Контроль доступу | Система повинна надавати доступ до книги лише її власнику та користувачам із наданою роллю (RBAC). | 0 успішних звернень до чужих ресурсів (IDOR) |
| <a id="srs-nfr-rel-01"></a>SRS-NFR-REL-01 | Доступність | Система повинна мати доступність не менше 99.5% на місяць. | Простій ≤ 3.6 год / 30 діб |
| <a id="srs-nfr-rel-02"></a>SRS-NFR-REL-02 | Доставка подій | Система повинна гарантувати доставку подій за схемою Outbox Pattern (at-least-once); споживачі повинні бути ідемпотентними. | 0 втрачених подій після недоступності брокера до 15 хв; 0 подвійних побічних ефектів |

## 5. Glossary

| Термін | Визначення |
|---|---|
| Outbox Pattern | Запис події в таблицю тієї ж транзакції БД, що й бізнес-зміна, з подальшою публікацією в брокер окремим процесом; гарантує доставку at-least-once. |
| Idempotency | Властивість обробника, за якої повторна обробка того самого повідомлення не змінює результат. |
| Latency p95 | Час відповіді, який не перевищують 95% запитів вибірки. |
| JWT | JSON Web Token: підписаний токен із claims, що використовується для автентифікації та авторизації. |
| OIDC | OpenID Connect: шар ідентифікації над OAuth 2.0. |
| Cypher | Декларативна мова запитів графової бази даних Neo4j. |
| RPO / RTO | Recovery Point Objective: допустима втрата даних у часі; Recovery Time Objective: допустимий час відновлення. |
