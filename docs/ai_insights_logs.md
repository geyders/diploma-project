## Лог №1: SRS (Завдання 1)

### 1. Початкова чернетка (імпорт з ЛР№4)

Пряме перенесення з розділу 1.5 без змін: 8 Core Features у формулюваннях на кшталт «Реалізувати реєстрацію та автентифікацію автора з керуванням профілем», матриця NFR із 4 рядків («Безпека: OAuth 2.0 / OIDC, JWT, GDPR, OWASP Top 10, Rate Limiting»), верифікація не описана.

### 2. Звіт ШІ-Аудитора

**1. Атомарність і чіткість функціональних вимог**

| Вимога | Помилка | Виправлення |
|---|---|---|
| CF1 «реєстрація та автентифікація автора з керуванням профілем» | Три системні дії в одному пункті | Розділити на реєстрацію, підтвердження, автентифікацію, зміну профілю |
| CF2 «створення та редагування ієрархічної структури з версіюванням» | Структура та версіювання змішані; відсутнє «видалення» й «відновлення версії» | Окремі вимоги для CRUD елементів, незмінної версії та відновлення |
| CF4 «асинхронну перевірку орфографії, граматики та пунктуації» | Не вказано тригер, механізм і відповідь клієнту | Вказати подію Kafka та HTTP 202 |
| CF6 «перевірку змістової узгодженості» | Не визначено вихід перевірки | Визначити перелік суперечностей із посиланням на сутність і фрагмент |
| CF1–CF8 | Модальне дієслово «Реалізувати» (імператив) замість «повинна» | Переформулювати за шаблоном «Система повинна…» |

**2. Вимірюваність NFR**

- «Rate Limiting» без числового порогу. Додати ліміт на користувача та код відповіді.
- «OWASP Top 10» не є метрикою. Замінити на «0 вразливостей Critical/High за SAST, DAST та SCA».
- «Latency p95 < 200 мс при 500 RPS» не прив'язано до середовища та набору ендпоінтів. Визначити еталонне середовище й обмежити синхронними ендпоінтами; додати допустиму частку помилок.
- «Доступність ≥ 99.5%» без періоду вимірювання. Вказати місяць і допустимий простій (3.6 год).
- «Щоденний backup» без RPO/RTO.
- «Outbox Pattern» є рішенням, а не вимогою. Сформулювати як гарантію доставки з вимірюваним критерієм.

**3. Верифікація.** Рекомендовано: k6 (навантаження, Spike), SonarQube (SAST), OWASP ZAP (DAST), Trivy (образи), gitleaks, Newman/Postman (API), Jest/pytest, Testcontainers, Prometheus.

**4. Gap Analysis.** Відсутні:
1. вимоги GDPR: право на видалення (ст. 17) та переносимість (ст. 20);
2. контроль доступу RBAC та захист від IDOR;
3. шлях надходження даних у граф: не визначено, хто виділяє сутності з тексту;
4. Fault Tolerance: retry, Circuit Breaker, Dead Letter Topic;
5. ідемпотентність споживачів при доставці at-least-once;
6. вимога до часу доставки результату клієнту;
7. структуровані журнали та `correlationId`;
8. вимога до TLS;
9. межа розміру графа для перевірки узгодженості.

### 3. Опрацювання зауважень

**Прийнято та виправлено:** усі зауваження п.1; додано числові пороги NFR (п.2); додано інструменти верифікації (п.3); додано FUN-05, 06 (GDPR), FUN-10 (RBAC), FUN-15 (виділення сутностей), NFR-SEC-04…06, NFR-REL-03, REL-04, PERF-03, PERF-04, OBS-01.

**Відхилено з обґрунтуванням [ПІДТВЕРДИТИ]:**
- Рекомендація щодо Kubernetes та реплікації БД відхилена: система розгортається в Docker Compose на одній машині, тому SRS фіксує еталонне середовище (розділ 1.3 SRS).
- Рекомендація додати Mutation Testing (PIT/Stryker) відхилена як така, що виходить за обсяг роботи.

**Відомий ризик:** до чернетки не внесено вимог до pgvector, згаданого в матриці розділу 1.3: жодна вимога його не використовує. Потрібне рішення: додати вимогу (семантичний пошук) або прибрати згадку з розділу 1.

## Лог №2: C4 Level 1–2 (Завдання 2)

### 1. Перші версії діаграм

Окремих «сирих» версій студентки в діалозі не було: діаграми Level 1–2 у `2_design.md` склав Claude як чернетку.

### 2. Звіт ШІ-Рев'юера (щодо чернетки `2_design.md`)

**1. Трасування на SRS.** Усі актори (ACT-01, 02) і зовнішній елемент EXT-01 відображені. Функції FUN-01…18 мають контейнер-власника (таблиця в 2.1). Зауваження: FUN-05 (видалення даних) і FUN-06 (експорт) стосуються одночасно Core API, Entity Graph та Keycloak, але на діаграмі відсутній механізм каскадного видалення в Neo4j. Рекомендація: подія `user.deletion.requested` у Kafka.

**2. Логіка контейнерів.** Контейнери є окремо розгортуваними одиницями, змішування з класами не виявлено. Зауваження:
- Outbox Relay входить до Core API; при падінні Core API події не публікуються. Допустимо, але зафіксувати як ризик.
- Keycloak використовує PostgreSQL спільно з Core API; для ізоляції рекомендовано окремий екземпляр БД.

**3. Зв'язки та протоколи.** Абстрактних підписів немає, протокол є у кожного `Rel`. Зауваження: зв'язок `spa → gw` поєднує REST і WSS в одному підписі; рекомендовано розділити на два зв'язки.

**4. Відмовостійкість і безпека.** Відсутні:
- Dead Letter Topic зазначено в описі Kafka, але не зображено окремо;
- агрегація журналів (Loki/ELK) для NFR-OBS-01;
- резервне копіювання як контейнер (cron-job для `pg_dump` та `neo4j-admin`) для NFR-REL-03;
- Kafka та Redis є одиничними точками відмови (replication factor 1).

### 3. Рішення студентки [ПІДТВЕРДИТИ]

- **Додати:** подію `user.deletion.requested` (FUN-05 повинна покривати Neo4j).
- **Відхилити:** окремий екземпляр PostgreSQL для Keycloak (ресурси еталонного середовища обмежені; ізоляція досягається окремою схемою).
- **Відхилити:** Loki/ELK та репліки Kafka/Redis; обґрунтування: обмежене локальне середовище. Ризик зафіксовано в ADR-001.
- **Додати:** контейнер резервного копіювання, якщо вистачає часу, або згадку в Розділі 3.

## Лог №3: C4 Level 3 (Завдання 3)

### 1. Перша версія

Первинну чернетку склав Claude.

### 2. Звіт ШІ-Аудитора (Entity Graph Service)

**1. Шари Clean Architecture.** Прямих зв'язків контролер → БД немає. Контролери залежать лише від Application Services. Порушення ізоляції не виявлено.

**2. SOLID та патерни.** Dependency Inversion дотримано: порти (`EntityRepository`, `EventPublisher`, `IdempotencyStore`) визначені в домені, адаптери їх реалізують. `ConsistencyRule` реалізує Strategy (OCP: нове правило не змінює `ConsistencyCheckService`). Зауваження:
- `ExtractedEntitiesConsumer` напряму викликає два Application Services; рекомендовано єдиний use case `ProcessExtractedEntitiesUseCase` для транзакційної межі;
- `ConsistencyRule` читає дані через `EntityRepository`, який також використовується для запису; розглянути розділення на Read- та Write-порти (CQS).

**3. Повнота пайплайну.** Присутні: DTO-валідація, GlobalExceptionFilter, TelemetryInterceptor. Зауваження: на діаграмі `TelemetryInterceptor` пов'язаний лише з `EntityController`; потрібно показати його застосування до `ConsistencyController`.

**4. Безпека.** Присутні `JwtAuthGuard` та `AccessGuard` (RBAC). Зауваження: відсутній компонент перевірки `aud`/scopes для виклику між сервісами (machine-to-machine).

### 3. Рішення студентки 

- **Прийняти:** єдиний use case для consumer (зменшує зв'язність).
- **Прийняти:** зв'язок `TelemetryInterceptor` з `ConsistencyController`.
- **Відхилити:** CQS-розділення портів: надлишкове для обсягу дипломної роботи.
- **Відхилити:** machine-to-machine автентифікацію: сервіси взаємодіють лише через Kafka та API Gateway.

## Лог №4: ADR-001 (Завдання 4)

### 1. Початкова чернетка

Чернетку склав Claude (рішення: Apache Kafka замість RabbitMQ). 

### 2. Звіт ШІ-Судді

**1. Аргументація.** Аргументи інженерні: порядок у партиції, retention, consumer groups. Зауваження: пункт 4 («узгодженість з Outbox Pattern») описує спільність підходу, а не перевагу Kafka: Outbox однаково працює з RabbitMQ. Рекомендовано видалити як аргумент.

**2. Альтернативи.** Для RabbitMQ додати Streams (з 3.9), що частково закриває вимогу повторного читання; обґрунтувати, чому цього недостатньо. Для варіанта C додати оцінку навантаження на PostgreSQL при кількості споживачів > 2.

**3. Наслідки.** Негативні наслідки наведені та чесні. Зауваження: відсутня кількісна оцінка споживання RAM (орієнтовно 1 ГБ потребує виміру); відсутній ризик перебалансування consumer group при перезапуску контейнера.

### 3. Підсумок студентки [ПІДТВЕРДИТИ]

- **Прийнято:** видалити аргумент №4 про Outbox; додати RabbitMQ Streams до альтернатив; виміряти реальне споживання RAM контейнером Kafka у Compose і замінити оцінку фактом.
- **Змінилося розуміння вибору:** Kafka обрано не за пропускною здатністю, а за порядком і повторною обробкою; при навантаженні ≤ 100 повідомлень/с це надлишкове рішення за ресурсами, і ADR прямо фіксує умови його перегляду.
