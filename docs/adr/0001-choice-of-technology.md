# ADR-001: Вибір брокера повідомлень для асинхронного конвеєра обробки тексту

| Параметр | Значення |
|---|---|
| Статус | **Approved** (Затверджено) |
| Дата | 28.10.2026 |
| Пов'язані вимоги | [SRS-FUN-13](../srs.md#srs-fun-13), [SRS-FUN-15](../srs.md#srs-fun-15), [SRS-NFR-PERF-02](../srs.md#srs-nfr-perf-02), [SRS-NFR-REL-02](../srs.md#srs-nfr-rel-02), [SRS-NFR-REL-04](../srs.md#srs-nfr-rel-04) |

## Context

Збереження фрагмента тексту ініціює конвеєр: перевірка мови та стилістика (NLP Analysis Service), виділення сутностей, оновлення графа та перевірка узгодженості (Entity Graph Service), доставка результатів клієнту (Realtime Service). Синхронна обробка блокує інтерфейс редагування (проблема As-Is №2, розділ 1.4), тому потрібен брокер повідомлень.

Обмеження, що випливають з SRS:

- гарантія доставки без втрат після недоступності брокера до 15 хв (NFR-REL-02);
- обробка події в межах одного фрагмента в порядку збереження версій;
- кілька незалежних споживачів однієї події (NLP, Realtime);
- можливість повторного аналізу історичних подій після зміни алгоритму;
- розгортання в Docker Compose на одній машині (4 vCPU, 16 ГБ RAM).

Очікуване навантаження на брокер становить до 100 повідомлень/с (оцінка: 500 RPS синхронних запитів, з яких лише збереження фрагментів породжують події). Така інтенсивність не є визначальним критерієм вибору: обидві технології її обслуговують.

## Alternatives

| Варіант | Переваги | Обмеження |
|---|---|---|
| **A. RabbitMQ 3.13 (quorum queues)** | Менше споживання пам'яті; гнучка маршрутизація (exchanges), TTL, пріоритети; вбудований Dead Letter Exchange | Повідомлення видаляється після підтвердження: повторний аналіз історії неможливий; для кількох споживачів потрібна окрема черга на кожного; порядок гарантується лише в межах однієї черги з одним споживачем |
| **B. Apache Kafka 3.x (KRaft)** | Лог із retention: повтор обробки за offset; порядок у межах партиції; consumer groups; незалежні споживачі без дублювання черг | Вища операційна складність; вища мінімальна пам'ять; Dead Letter Topic і повторні спроби реалізуються на рівні застосунку |
| **C. Polling Outbox-таблиці без брокера** | Відсутність додаткової інфраструктури | Навантаження на PostgreSQL зростає з кількістю споживачів; відсутня семантика consumer groups; затримка визначається інтервалом опитування |

## Decision

Обрано **Apache Kafka у режимі KRaft** (один брокер у Docker Compose).

Обґрунтування:

1. **Порядок подій.** Ключ повідомлення `fragmentId` спрямовує всі події фрагмента в одну партицію; порядок версій зберігається при кількох інстансах споживача.
2. **Повторна обробка.** Retention 7 діб дозволяє перезапустити NLP-аналіз з довільного offset без повторного збереження текстів (потрібно для регресійного порівняння версій алгоритму в Розділі 3).
3. **Незалежні споживачі.** Події `analysis.completed` та `consistency.checked` споживаються Realtime Service через власну consumer group без додаткових черг.
4. **Надійність публікації.** Outbox Relay публікує події з `acks=all` та `enable.idempotence=true`; споживачі ідемпотентні через Redis (`SET NX EX`) за `messageId`.

RabbitMQ Streams (з версії 3.9) надають журнал із повторним читанням і частково закривають вимогу повторної обробки. Вони не були обрані, оскільки порядок за ключем розподіляється між партиціями лише через окремий механізм Super Streams, а екосистема клієнтів і інструментів моніторингу consumer lag менш зріла, ніж у Kafka.

Топіки: `text.fragment.saved`, `analysis.completed`, `entities.extracted`, `consistency.checked`, `book.access.changed`, `*.dlt` (Dead Letter Topic).

## Consequences

### Позитивні

- Відтворюваність: будь-яку подію можна обробити повторно в межах retention.
- Масштабування споживачів збільшенням кількості партицій без зміни топології.
- Порядок подій фрагмента гарантується архітектурно, а не логікою застосунку.

### Негативні

- **Відсутність відмовостійкості брокера.** Один брокер із replication factor 1 є єдиною точкою відмови. Це обмежує досяжність NFR-REL-01 (99.5%) і потребує явного зазначення в Розділі 3: доступність вимірюється для одновузлового розгортання.
- **Надлишковість для поточного навантаження.** При ≤ 100 повідомлень/с RabbitMQ є достатнім за пропускною здатністю; вибір Kafka зумовлений порядком і повторною обробкою, а не продуктивністю.
- **Ресурсні витрати.** Брокер із JVM споживає орієнтовно 1 ГБ RAM, що зменшує запас еталонного середовища для k6-тестування NFR-PERF-01.
- **Реалізація на рівні застосунку.** Retry, Dead Letter Topic та Circuit Breaker (NFR-REL-04) відсутні «з коробки» й потребують коду та тестів.
- **At-least-once.** Дублікати повідомлень неминучі; усі споживачі повинні бути ідемпотентними, що збільшує обсяг коду та тестів.
- **Операційна складність.** Необхідні моніторинг consumer lag, керування retention, обробка перебалансування груп; ускладнення CI/CD (додатковий контейнер у інтеграційних тестах).
- **FinOps.** У разі перенесення в хмару керований Kafka-сервіс має вищу вартість за годину, ніж керований брокер AMQP. Ризик Vendor Lock-in знижується використанням відкритого протоколу Kafka (можлива заміна на сумісні реалізації).

### Умови перегляду рішення

Рішення переглядається, якщо після Розділу 3 повторна обробка історії не буде використана, або ресурсні витрати брокера унеможливлять виконання NFR-PERF-01 у еталонному середовищі.
