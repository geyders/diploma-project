# Розділ 1. Аналіз аналогів та технічне завдання

## 1.2 Аналіз існуючих аналогів

### 1.2.1 Інженерний опис аналогів

**Grammarly**

Grammarly реалізовано як хмарний сервіс на основі мікросервісної архітектури, що надає доступ до функціоналу через REST API з автентифікацією за протоколом OAuth 2.0. ML-інфраструктура компанії розгорнута на кластерах Kubernetes з оркестрацією через Argo CD, що забезпечує масштабоване виконання моделей перевірки граматики та стилю. Технічним обмеженням системи є фокус виключно на аналізі поверхневого рівня тексту (граматика, пунктуація, стиль) за відсутності структурованої моделі сутностей твору (персонажів, локацій, подій), що унеможливлює перевірку змістової узгодженості сюжету.

**Scrivener**

Scrivener побудовано як десктопний застосунок (macOS/Windows/iOS) з локальним зберіганням даних у власному бінарному форматі проєкту (пакет .scriv), без центрального серверного бекенду. Синхронізація між пристроями реалізована на рівні файлової системи через сторонні хмарні сховища (Dropbox, iCloud), а не через API. Архітектура є однокористувацькою (single-user): застосунок не передбачає одночасної багатокористувацької роботи над проєктом. Технічними обмеженнями системи є відсутність автоматизованого NLP-аналізу тексту, ризик конфліктів файлової синхронізації при паралельному редагуванні з кількох пристроїв, а також відсутність будь-якого механізму перевірки змістової узгодженості сюжету.

**Sudowrite**

Sudowrite реалізовано як хмарний веб-застосунок, що надає доступ до кількох LLM-провайдерів (власна модель Muse, а також Claude, GPT, Gemini) через їхні API для генерації та редагування тексту. Функція Story Bible реалізує збереження контексту персонажів, сюжету та світу твору у формі, що передається в промпт моделі, без окремої структурованої бази даних сутностей. Публічний API для сторонніх розробників відсутній. Технічним обмеженням системи є залежність продуктивності та вартості обробки від зовнішніх LLM-провайдерів, а також те, що перевірка узгодженості спирається на обмежене вікно контексту моделі, а не на детерміновані запити до структурованої моделі даних, що знижує надійність виявлення суперечностей при значному обсязі твору.

### 1.2.2 Порівняльна інженерна матриця

| Критерій | Novelize | Grammarly | Scrivener | Sudowrite |
|---|---|---|---|---|
| Тип архітектури | Мікросервісна, event-driven | Мікросервісна, хмарна | Десктопний монoліт, локальний | Хмарний застосунок, LLM-оркестрація |
| Протоколи обміну (API) | REST, WebSocket/SSE | REST, OAuth 2.0 | Файлова синхронізація (без API) | REST до LLM-провайдерів (закритий) |
| СУБД | PostgreSQL, Neo4j, pgvector | Не публікується | Локальний файл проєкту (.scriv) | Не публікується |
| Відмовостійкість | Outbox Pattern, асинхронна черга (Kafka/RabbitMQ) | Kubernetes-оркестрація, Argo CD | Відсутня (ризик конфліктів синхронізації) | Залежить від відмовостійкості провайдера LLM |
| Перевірка узгодженості сутностей | Графові запити (Neo4j) | Відсутня | Відсутня | Обмежена вікном контексту LLM |
| Хмарна інфраструктура | Docker, CI/CD (GitHub Actions) | Kubernetes, AWS (EFS/S3) | Відсутня (десктоп) | Хмарна, мультипровайдерна (LLM API) |

### 1.2.3 Аналітичний висновок

Проаналізовані аналоги вирішують задачі текстового аналізу та структурування твору ізольовано одна від одної. Grammarly демонструє зрілу мікросервісну архітектуру з масштабованою ML-інфраструктурою, проте обмежується аналізом поверхневого рівня тексту без моделі сутностей твору. Scrivener не має серверного бекенду, що унеможливлює автоматизований аналіз та несе ризик конфліктів синхронізації при багатопристрійній роботі. Sudowrite реалізує функцію пам'яті сюжету через контекст LLM-провайдера, однак цей підхід не гарантує детермінованого виявлення суперечностей при зростанні обсягу твору, оскільки обмежений розміром вікна контексту моделі.

У межах кваліфікаційної роботи передбачено усунення виявлених обмежень шляхом поєднання структурованого графового моделювання сутностей твору (Neo4j) з асинхронною мікросервісною обробкою NLP-аналізу (Apache Kafka, spaCy/NLTK/LanguageTool). На відміну від Sudowrite, перевірка змістової узгодженості реалізується як детермінований запит до графової бази даних, а не як залежність від обмеженого контексту LLM. На відміну від Scrivener, забезпечується серверна архітектура з підтримкою асинхронної обробки без ризику конфліктів файлової синхронізації. Порівняно з Grammarly, розширюється предметна область аналізу від поверхневого рівня тексту до моделі сутностей твору та зв'язків між ними.

## 1.5 Модель To-Be та функціональні вимоги

Цільова модель (To-Be) передбачає трансформацію процесів, описаних у моделі As-Is, шляхом впровадження централізованого графового реєстру сутностей твору та асинхронного конвеєра обробки природної мови. Структурування та перевірка узгодженості виконуються як автоматизовані, детерміновані операції над графовою моделлю даних. Контроль якості тексту винесено в окремий сервіс, що обробляє запити асинхронно через чергу повідомлень, не блокуючи інтерфейс редагування.

### Функціональні вимоги (Core Features)

1. Реалізувати реєстрацію та автентифікацію автора з керуванням профілем.
2. Забезпечити створення та редагування ієрархічної структури твору (книга → розділ → сцена → фрагмент) з версіюванням правок.
3. Реалізувати реєстр сутностей твору (персонажі, локації, події, хронологія) у графовій моделі даних.
4. Реалізувати асинхронну перевірку орфографії, граматики та пунктуації через чергу повідомлень.
5. Реалізувати стилістичний аналіз тексту (повтори слів, довжина речень, метрики читабельності).
6. Реалізувати перевірку змістової узгодженості твору шляхом графових запитів до реєстру сутностей.
7. Реалізувати доставку результатів асинхронного аналізу в реальному часі через WebSocket-з'єднання.
8. Забезпечити моніторинг стабільності сервісів та метрик затримок обробки.

### Нефункціональні вимоги (NFRs)

| Категорія | Метрика |
|---|---|
| Продуктивність | Latency p95 < 200 мс при 500 RPS (синхронні ендпоінти) |
| Обробка тексту | Асинхронний аналіз до 50 000 символів — не довше 30 с |
| Безпека | OAuth 2.0 / OIDC, JWT, GDPR, OWASP Top 10, Rate Limiting |
| Надійність | Outbox Pattern, Docker, доступність ≥ 99.5%, щоденний backup |

### Постановка задачі

Таким чином, метою кваліфікаційної роботи є проєктування та розробка мікросервісної інформаційної системи Novelize для вирішення задачі автоматизованого контролю структурної та змістової цілісності художніх текстів у процесі їх створення та редагування.
