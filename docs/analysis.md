# Розділ 1. Аналіз аналогів та технічне завдання

## 1.2 Аналіз існуючих аналогів

### 1.2.1 Інженерний опис аналогів

**Grammarly**

Grammarly реалізовано як хмарний сервіс на основі мікросервісної архітектури, що дозволяє масштабувати компоненти обробки тексту незалежно одна від одної. Доступ до функціоналу забезпечується через REST API з автентифікацією за протоколом OAuth 2.0. ML-інфраструктуру розгорнуто на кластерах Kubernetes з оркестрацією через Argo CD, що забезпечує масштабоване виконання моделей перевірки граматики та стилю. Інформація щодо використаних СУБД та механізмів консистентності даних не розкривається. Технічним обмеженням системи є аналіз виключно поверхневого рівня тексту (граматика, пунктуація, стиль) за відсутності структурованої моделі сутностей твору (персонажів, локацій, подій), що унеможливлює перевірку змістової узгодженості сюжету.

**Scrivener**

Scrivener побудовано як десктопний застосунок (macOS/Windows/iOS) з локальним зберіганням даних у власному бінарному форматі проєкту (пакет .scriv) без центрального серверного бекенду. Така архітектура виключає горизонтальне масштабування. Синхронізація між пристроями реалізована на рівні файлової системи через сторонні хмарні сховища (Dropbox, iCloud), а не через API, тому механізми транзакційної консистентності даних відсутні. Архітектура є однокористувацькою (single-user) і не передбачає одночасної багатокористувацької роботи над проєктом. Технічними обмеженнями системи є відсутність автоматизованого NLP-аналізу тексту, ризик конфліктів файлової синхронізації при паралельному редагуванні з кількох пристроїв та відсутність механізму перевірки змістової узгодженості сюжету.

**Sudowrite**

Sudowrite реалізовано як хмарний веб-застосунок, що забезпечує доступ до кількох LLM-провайдерів (власна модель Muse, а також Claude, GPT, Gemini) через їхні API для генерації та редагування тексту. Масштабування обробки делеговано зовнішнім провайдерам. Функція Story Bible зберігає контекст персонажів, сюжету та світу твору у формі, що передається в промпт моделі, без окремої структурованої бази даних сутностей. Публічний API для сторонніх розробників відсутній, інформація щодо використаних СУБД не розкривається. Технічними обмеженнями системи є залежність продуктивності та вартості обробки від зовнішніх LLM-провайдерів, а також те, що перевірка узгодженості спирається на обмежене вікно контексту моделі, а не на детерміновані запити до структурованої моделі даних. Це знижує надійність виявлення суперечностей при значному обсязі твору.

### 1.2.3 Аналітичний висновок підрозділу 1.2

Проаналізовані аналоги вирішують задачі текстового аналізу та структурування твору ізольовано. Grammarly використовує розподілену мікросервісну архітектуру з масштабованою ML-інфраструктурою, проте обмежується аналізом поверхневого рівня тексту без моделі сутностей твору. Scrivener не має серверного бекенду, що унеможливлює автоматизований аналіз і створює ризик конфліктів синхронізації при багатопристрійній роботі. Sudowrite реалізує пам'ять сюжету через контекст LLM-провайдера; цей підхід не гарантує детермінованого виявлення суперечностей при зростанні обсягу твору через обмеження розміру вікна контексту моделі.

У межах кваліфікаційної роботи передбачено запозичення мікросервісної декомпозиції та контейнеризованого розгортання, реалізованих у Grammarly, з доповненням їх графовим моделюванням сутностей твору (Neo4j) і асинхронною обробкою NLP-аналізу (Apache Kafka, spaCy/NLTK/LanguageTool). На відміну від Sudowrite, перевірка змістової узгодженості виконується як детермінований запит до графової бази даних, а не залежить від обмеженого контексту LLM. На відміну від Scrivener, забезпечується серверна архітектура з асинхронною обробкою без ризику конфліктів файлової синхронізації.

Обраний підхід передбачає компроміс: зростання операційної складності (брокер повідомлень, поліглотна персистентність PostgreSQL/Neo4j/pgvector, eventual consistency між сервісами) зумовлює потребу в Outbox Pattern та спостережуваності, проте забезпечує горизонтальне масштабування й відтворюваність результатів перевірки. Детальне проєктування архітектури та взаємодії сервісів наведено в Розділі 2.
